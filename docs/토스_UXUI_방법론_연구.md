# 토스(Toss)는 어떻게 지금의 UX/UI 수준에 도달했는가

> 모바일 보상형 리서치 앱 **잇츠미**의 화면 개편을 위한 레퍼런스 연구.
> 1차 출처: 토스 기술/디자인 블로그(toss.tech), 토스 디자인 시스템(TDS) 공개 아티클.
> 목적: "토스 이상"의 모바일 UX/UI 품질 기준을 정의하고, 잇츠미 화면을 이 기준으로 재단(裁斷)한다.

---

## 0. 요약 (Executive Summary)

토스의 완성도는 영감이 아니라 **반복 가능한 시스템**에서 나온다. 핵심은 세 가지다.

1. **패턴화** — 실제 사용 데이터를 모아 "예외처럼 보이던 케이스"를 정식 패턴으로 흡수한다.
2. **심미적 경험 설계** — 등장·퇴장·터치 등 미시 인터랙션의 투명도/위치/속도/가속도를 수치로 규정한다.
3. **모든 유저의 사용성** — 다크모드 1:1 팔레트, 큰 텍스트, 스크린리더(보이스오버/톡백)를 컴포넌트 단에서 보장한다.

> 디자이너가 "다크모드·긴 텍스트·접근성"을 매번 직접 결정하면 같은 컴포넌트가 서비스마다 다른 경험을 낳는다. 토스는 이를 **디자인 시스템(TDS)**으로 끌어올려, 메이커는 레고처럼 조립만 하면 일관·완성된 경험이 나오도록 만들었다. (출처: toss.tech "토스 디자이너가 제품에만 집중할 수 있는 방법")

## 1. 토스의 진화 과정 (연대기적 관점)

| 단계          | 문제의식                                                         | 해법                                           | 잇츠미 시사점                           |
| ------------- | ---------------------------------------------------------------- | ---------------------------------------------- | --------------------------------------- |
| 초기          | 송금 1건을 "3번 터치 안에" — 금융의 복잡성을 소비자 단순함으로   | 단일 핵심 동선 집착, 불필요 단계 제거          | 설문 응답 동선을 최소 터치로            |
| 컴포넌트화    | 화면마다 OS 기본형을 조금씩 변형 → 비일관                        | 공용 컴포넌트 라이브러리 도입                  | `.pm-*` 컴포넌트의 토큰 일관성          |
| 패턴 고도화   | 컴포넌트가 못 받는 예외 케이스 급증(긴 텍스트, 7개 이상 항목 등) | 실사용 분석 → 패턴 추가(체크형/스크롤 흐림 등) | 빈 상태·긴 목록·에러를 정식 패턴으로    |
| 시스템화(TDS) | 다크모드·접근성을 디자이너가 매번 수기 결정                      | 토큰·정책을 시스템이 보장                      | **다크모드 토큰 1:1 또는 단일 테마 락** |

**핵심 통찰**: 토스는 "예쁜 화면"을 한 번 만든 게 아니라, **예쁜 화면이 자동으로 나오는 규칙**을 만들었다. 개편의 목표도 "이 화면 하나"가 아니라 "이 규칙을 잇츠미에 이식"하는 것이어야 한다.

## 2. 세 가지 설계 축 (TDS 공개 사례 정리)

### 2-1. 다양한 케이스를 패턴화한다

- **실사용 데이터 수집 후 패턴 결정**: "오른쪽 체크 아이콘이 50% 가까이 쓰인다" → 기본형/아이콘형 외 **체크형**을 정식 추가하고 체크는 왼쪽 배치로 인지성↑.
- **긴 텍스트 대비**: 4자 이하 가정이 틀렸다(5자↑ 절반, 7자↑도 상당). → min/max 너비를 화면 비율(%) 기준으로 보장, 위계에 맞춰 텍스트 크기 조정.
- **목록이 길어질 때**: 7개 이상이면 스크롤 인지가 안 돼 탐색 실패(시니어 VoC). → 목록 위·아래 **흐림(fade) 효과**로 "더 있다"를 암시.

> 잇츠미 적용: **출생연도 60개를 그리드로 펼치는 것**은 정확히 토스가 경계한 "긴 목록을 인지 보조 없이 노출"하는 안티패턴. → 스크롤 스냅 휠 + 중앙 밴드 + 상·하 페이드로 교체(이번 개편 반영).

### 2-2. 심미적인 경험을 설계한다

- **무거움 제거**: 위로 뜨는 요소는 배경 블러 + 밝은 외곽선으로 "유리처럼 가볍게".
- **정성적 인터랙션**: 터치 시 누른 지점에서 자연스럽게 뜨도록 투명도·위치·속도·가속도를 사전 수치화. 등장 시 페이드도 동기화.
- **OS 기본형 탈피**: "OS 모양에서 살짝 바꾼" 수준이 아니라 완결된 자체 디자인.

> 잇츠미 적용: 터치 시 `:active` 배경 한 단계 진하게 + scale 다운(M2 반영). 바텀시트/토스트는 가벼운 등장. 정령/알은 OS 기본이 아닌 자체 SVG 아이덴티티 유지.

### 2-3. 모든 유저의 사용성을 지킨다

- **큰 텍스트/해상도**: 고정 px이 아니라 단위/비율로 받아 텍스트와 아이콘 위계가 함께 커지도록.
- **스크린리더**: 열림/닫힘 초점 지정, 투명 닫기 버튼, 장식 아이콘은 읽지 않기 등 5규칙을 컴포넌트에 내장.
- **다크모드**: **다크 전용 색상 팔레트를 만들어 1:1 자동 대응.** (← 이게 핵심)

> 잇츠미 적용: 라이트 프레임 + OS 다크 토큰이 충돌해 "반쪽 다크"가 되던 문제를, **모바일 앱은 단일 라이트 테마로 락(`.pm-root` 토큰 재고정)**해 일관성 확보(이번 개편 반영). 향후 정식 다크 팔레트를 1:1로 추가하면 락을 해제 가능.

## 3. 잇츠미에 적용할 "토스 기준" 체크리스트

화면을 뜯을 때마다 아래 9개 질문을 통과해야 한다.

1. **단일 핵심 동선**이 한눈에 보이는가? (주 CTA 1개, 보조는 위계 강등)
2. **긴 목록/긴 텍스트**에 인지 보조(페이드·min/max·휠)가 있는가?
3. **터치 피드백**(배경 진해짐 + scale)이 모든 인터랙션에 있는가?
4. **등장/퇴장**이 동기화된 가벼운 모션인가? (reduced-motion 가드 포함)
5. **색 토큰이 일관**된가? (하드코딩 색 금지, 다크 충돌 없음)
6. **폰트 가시성**: 배경 대비 대비비(WCAG AA 4.5:1)를 만족하는가?
7. **터치 타깃** ≥ 44×44 인가?
8. **스크린리더**: 초점·aria-label·장식 aria-hidden이 정확한가?
9. **빈 상태/로딩/에러**가 본 화면과 같은 격으로 디자인됐는가?
