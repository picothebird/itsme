## 0. 결론 요약 (Executive Summary)

현재 코드가 따르는 **실제 디자인 언어는 Notion**이다. `--color-primary: #5645d4`, 파스텔 `--tint-*` 카드, Pretendard(Inter 계열) 타이포가 모두 [notion/DESIGN.md](../notion/DESIGN.md)와 정확히 일치한다. 따라서 "Apple Action Blue(#0066cc)와 다르다"는 것은 **버그가 아니라 의도된 선택**이며, 크리틱의 기준선은 Notion 시스템으로 둔다.

문제의 본질은 _색상_ 이 아니라 **시스템 규율(discipline)의 부재**다. 최근 빠르게 붙인 표면들이 (1) 다른 네임스페이스의 클래스를 빌려 쓰고, (2) 토큰 대신 하드코딩 값을 쓰고, (3) 동일 패턴(닫기/뒤로, 빈 상태, 섹션 헤딩, 상태 배지)을 화면마다 다르게 구현했다. 그 결과 "기능은 되는데 한 제품처럼 보이지 않는다."

우선순위(영향도×비용):

1. **P0 — 공통 프리미티브 통일**: 섹션 헤딩·빈 상태·상태 배지·카드 톤을 네임스페이스 중립 클래스로 통합. (낮은 비용, 전 화면 일관성 즉시 상승)
2. **P1 — 유저앱 참여/정령 탭 재정렬**: 차용 클래스 제거, 카피 톤·여백·버튼 위계 정리.
3. **P1 — 리서처 관리 리서치/시맨틱 패널 대칭화**: 닫기/뒤로 패턴, 진행 단계 시각화, Notion 카드(보더 기반) 정합.
4. **P2 — 토큰 하드코딩 제거 + 데드 CSS 정리**.

## 1. 디자인 언어 정합성 (Brand Integrity)

### 1.1 [확인됨] 구현은 Notion 언어를 따른다

- `--color-primary #5645d4` = Notion `primary`, `--color-primary-pressed #4534b3` = Notion `primary-pressed`.
- `--tint-peach/rose/mint/lavender/sky/yellow` = Notion `card-tint-*` 6종 정확히 일치.
- 시맨틱 `--color-success #1aae39`, `--color-warning #dd5b00`, `--color-danger #e03131` = Notion 시맨틱 3종 일치.
- **권고**: DESIGN.md(Apple)는 _연구자 랜딩/마케팅_ 표면 전용으로 범위를 명문화하고, 앱/백오피스 UI의 단일 진리원천은 notion/DESIGN.md로 선언한다. (혼선 종식)

### 1.2 [갭] 라운드(radius) 스케일이 Notion과 어긋남

- Notion: `sm 6 / md 8 / lg 12 / xl 16 / xxl 20`. 코드: `--radius-md 12 / --radius-lg 16`.
- Notion **버튼은 md(8px)**, **카드는 lg(12px)**. 코드의 `.pm-btn`은 14px 하드코딩, 카드들은 16px(`--radius-lg`).
- 결과: 버튼이 Notion보다 둥글고(말랑), 카드가 더 둥글다 → "Notion다움"이 흐려짐.
- **권고**: 토큰 자체를 Notion 스케일로 재정렬하거나(파급 큼), 최소한 신규 표면은 버튼=`--radius-md`, 카드=`--radius-lg`로 통일하고 하드코딩 14/16px 제거.

### 1.3 [갭] 카드 표현 방식 이원화

- Notion `card-base`: **흰 배경 + 1px hairline 보더 + radius lg + padding xl(24)**.
- 코드 `.card`: soft 배경 + 보더 없음(섀도우 의존)인 반면, 신규 `.rs-study`/`.rs-app`/`.sem-card`/`.pm-study-card`는 보더가 있음 → **한 화면에 두 카드 철학 공존**.
- **권고**: 카드 1종 표준(보더 기반 Notion 카드)으로 수렴. 강조는 `--tint-*` 배경으로만.

## 2. 정보구조 & 유저 플로우 (UX Research 관점)

### 2.1 유저앱 4탭 — 참여/정령의 역할 경계가 모호

- 탭: 설문(deck) / 참여(tasks) / 정령(pet) / 상점(shop).
- **문제**: "참여" 탭 최상단이 다시 "대기 중인 설문 N개 → 참여" 카드로 deck으로 되돌린다. deck 탭과 기능이 겹쳐 _왜 두 곳에서 같은 일을 하나_ 라는 인지 비용 발생.
- **문제**: "신청형 관리 리서치"(인터뷰/UT/다이어리)는 즉시참여 설문과 보상·소요·선정 절차가 전혀 다른데, 같은 탭에서 같은 카드 톤으로 섞여 위계가 안 보인다.
- **권고**:
  - 참여 탭을 *신청형 리서치 허브*로 정체화. 상단 deck 되돌리기 카드는 "오늘의 빠른 설문" 1줄 배너로 축소(보조 동선)하고, 본문은 "내 신청 현황 → 신청 가능한 리서치" 중심.
  - 신청형 카드에 **절차 스텝(신청→스크리닝→선정→일정→완료)** 미니 스테퍼를 노출해 "지금 어디"인지 즉시 인지.

### 2.2 상태 모델은 9단계인데 사용자 피드백은 배지 한 줄뿐

- `applied→screening→review→selected→scheduled→in_session→completed→paid`(+rejected).
- **문제**: 사용자는 배지 텍스트만 본다. 다음에 뭘 해야 하는지(예: 일정 확정 대기, 세션 참여 준비)가 없다.
- **권고**: 상태별 **다음 행동 한 줄 안내**(예: selected→"일정 조율을 기다려 주세요") + 진행 스테퍼. 거절(rejected)은 사유/재신청 가능 시점 안내.

### 2.3 리서처 관리 리서치 콘솔 — 단계 전이가 "버튼 나열"

- 신청자 카드에 다음 가능 상태가 버튼으로 평면 나열(검토/선정/거절 …).
- **문제**: (1) 되돌리기/취소 동선 없음, (2) 일괄 선택/일괄 전이 없음(정원 8명을 1명씩), (3) 스크리너 응답 *개수*만 보이고 *내용*을 못 봐서 선정 판단 근거가 없음.
- **권고(이번 범위 일부 + 로드맵 4.2)**: 스크리너 응답 펼치기, 상태 스테퍼 표시, 위험 액션(거절)은 ghost+확인. 일괄 처리는 4.2로 명시.

### 2.4 대칭성 결여 — 닫기/뒤로 패턴

- 인사이트의 분석 카드에는 "닫기"가 있는데, 관리 리서치의 신청자 패널에는 선택 해제 동선이 없다.
- **권고**: 선택형 상세 패널은 모두 우상단 닫기(X) 또는 "← 목록" 일관 적용.

## 3. 컴포넌트·시각 일관성 (Design 관점)

### 3.1 [핵심 결함] 네임스페이스 차용

- `TasksStage`가 **`.pm-shop__heading`(상점)**, **`.pm-pet__empty`(정령)**을 빌려 씀. ([PanelistMobile.tsx](../apps/frontend/src/features/PanelistMobile.tsx))
- **문제**: 상점 헤딩 스타일을 바꾸면 참여 탭이 깨진다(은닉 결합). 빈 상태 아이콘/카피가 의미와 무관하게 정령 톤으로 노출.
- **권고**: 네임스페이스 중립 공통 클래스 신설 — `.pm-section-title`(섹션 헤딩), `.pm-empty`(아이콘+카피 빈 상태). 모든 탭이 이를 공유.

### 3.2 버튼 위계 단조

- 참여/정령의 모든 카드 CTA가 `pm-btn--primary`. 1차 행동이 화면당 5~6개 → 시선 분산, "무엇이 진짜 다음 행동인지" 상실.
- **권고**: 화면당 primary 1~2개 원칙. 반복 리스트의 행 액션은 secondary/ghost로 강등. 위험·취소는 ghost.

### 3.3 빈 상태(empty state) 3종 난립

- 일반 `.empty`(리서처), `.pm-pet__empty`(유저), 텍스트만 `.pm-muted`("불러오는 중...") 혼용. 높이·아이콘·카피 톤 제각각.
- **권고**: 로딩=스켈레톤/공통 스피너, 빈 상태=아이콘+제목+보조문구 1세트로 표준화(유저/리서처 각 1개).

### 3.4 상태 배지 색 토큰화 누락

- `.rs-app__status--stop`은 `#d23f57`/`#fdeef0`, `.sem-dup`은 `#fff8e8`/`#b8860b`/`#fbe3a8` 하드코딩.
- 동일 의미의 유저측 `.pm-app-status--stop`은 `--color-...` 계열과 또 다른 값.
- **권고**: 상태 톤 4종(wait/go/stop/done)을 토큰화(`--tone-stop-fg/bg` 등)하고 유저·리서처가 동일 토큰 사용. 의미 일치 → 색 일치.

### 3.5 시맨틱 유사·중복 패널 마감도

- 점수가 텍스트 %만. 분석 카드의 `.analytics-bar__fill`처럼 막대 시각화가 없어 옆 카드와 마감 격차.
- 중복 쌍 카피가 "{a} / {b}"로 길어 한 줄 잘림(ellipsis)에 의존 → 정보 손실.
- **권고**: 점수 막대(또는 도넛) 추가, 중복 쌍은 2줄 레이아웃(Q번호 + 문항 텍스트 각각). "왜 중복인지" 임계값(0.82) 안내 툴팁.

## 4. 카피·보이스 톤 (Content Design)

- 동일 제품에서 표현 결이 갈린다: 참여="설문/참여", 정령="데이터 조각/먹이기", 상점="기프티콘 교환". 게임화(정령)와 거래(상점)와 노동(설문)이 한 앱에서 서로 다른 인격으로 말한다.
- **권고**: 보이스 1원칙 정의 — "친근하되 과장 없는 존댓말, 보상은 명확히, 게임화는 거들 뿐". 마이크로카피 사전(빈 상태/로딩/성공/실패/위험) 표준화.

## 5. 접근성·반응형 (빠른 점검)

- 상태 배지가 **색만으로** 의미 전달(색맹 사용자 구분 약함) → 텍스트 라벨은 있으나 톤 대비 점검 필요.
- 리서처 신청자 카드의 다중 액션 버튼이 좁은 폭에서 가로 압착 → wrap/세로 정렬 규칙 필요.
- 시맨틱 중복 쌍 ellipsis는 모바일·내로우에서 정보 손실.
- **권고**: 배지에 아이콘 보조, 액션 버튼 flex-wrap, 텍스트 2줄 허용.
